## 1. Verdict

**PASS WITH FINDINGS**

The change is materially built: all four migrations, the model, the validator, the runner, the cache, three endpoints, the billing resource, the sweeper cron, the frontend component, store, `/profile` slot and a fully key-parity i18n block are on disk, and both suites are green (`152/152` adaptation tests, `484 passed / 1 failed` full backend, `48/48` frontend, `0 errors` svelte-check). Ten of the twenty-one spec requirements are fully met and the billing chain (`bill-R1`…`bill-R5`) is the strongest part of the delivery. It is not a PASS, for three reasons. First, the change's own headline invariant — the honesty guardrail — is shipped in one layer instead of two: **there is no JD sanitization anywhere in the backend**, so the `cvA-R4` prompt-injection scenario has zero implementation and zero tests. Second, the design's closed decision `D2` (auto-invalidation of the adaptation cache on CV edit) **is a tautology and can never fire**, and the test that appears to prove it passes for the wrong reason — after editing a CV, a repeat POST inside the 24 h window still returns the pre-edit adaptation. Third, the response contract shipped is materially different from the four spec files (no `poll_url`, no `{current_tier, limit, upgrade_url}`, `NO_CV_FOUND` instead of `CV_NOT_FOUND`, `/v1/adaptations/by-cv/{id}` instead of `/v1/cvs/{id}/adaptations`, `outreach`/`brief` absent instead of `null`), which means the specs on disk do not describe the deployed API. None of these is a security or data-loss regression in the audited paths, and none is caused by the four implementing commits alone; but the specs are not currently a contract, and the artifact set claims considerably more than the code delivers. `tasks.md` reading 0/37 is misleading in both directions — most tasks did ship, several did not, and a few shipped as something materially different from what they say.

## 3. Findings

### CRITICAL

**F1 — `content_version` cache invalidation is a no-op; after editing a CV, a repeat request inside 24 h serves the pre-edit adaptation. The test that appears to prove it is tautological.**

- **Evidence.** `backend/app/api/v1/adaptations.py:290-295` calls `get_cached(..., content_version=cv.content_version, ...)`, where `cv` was loaded from `users_cvs` in this same request at `:279`. Inside `get_cached`, the `WHERE` clause filters on `(parent_cv_id, jd_text_hash, status, created_at >= threshold)` only — there is no `content_version` predicate (`backend/app/services/adaptation_cache.py:106-118`). The "defensive" check at `:123-134` re-reads the *same* `users_cvs` row in the *same* session and compares `cv_obj.content_version != content_version`, i.e. it compares the database value against itself. It can only fail if a caller passes a version that contradicts the database, which the sole production caller never does. There is also nothing for it to compare: **`cv_adaptations` has no `content_version` column.** Migration 015 (`backend/alembic/versions/015_cv_adaptations.py:53-91`) does not create one, no later migration adds one, and the model declares none (`backend/app/db/models.py:688-776`) even though its docstring at `:701-703` claims PR2 adds it.
- **Why it matters.** The cache serves `adapted_cv_json` verbatim from the completed row (`adaptations.py:303-306`). A user who corrects their CV and re-runs the same job description receives their *old* CV back with `status: completed`, and the frontend renders it as a fresh success (`frontend/src/routes/profile/+page.svelte:448-452`). The product's headline promise is honesty; serving an artifact derived from content the user has already retracted is a correctness defect a user cannot detect. It is precisely the risk the proposal named and deferred to the design (`proposal.md` §Risks: "Cache dedupe sirve resultado obsoleto tras editar CV — Media — Hash incluye `cv_id` + invalidación al editar el CV fuente") and the risk `design.md` §12 R5 claims is "mitigated by construction".
- **Why the suite does not see it.** `tests/test_adaptation_cache.py:251-273` (`test_different_content_version_invalidates_cache`) passes `content_version=2` while the fixture CV sits at `content_version=1` (`:101`). That makes the defensive check fire and the test pass — but the production caller passes `cv.content_version`, i.e. the same number the function re-reads. The test asserts a behaviour that only a mis-caller can trigger, and its docstring ("then the CV was edited (bumped to content_version=2), then the same request comes in") describes a scenario the code does not implement. There is **no** test anywhere that edits a CV and then repeats the POST. A green test is masking a broken requirement.
- **Fix.** Add `content_version INT NOT NULL` to `cv_adaptations` in a new migration (e.g. `022_cv_adaptations_content_version`), snapshot `cv.content_version` at INSERT (`adaptations.py:320-327`), and add `CVAdaptation.content_version == content_version` to the `get_cached` predicate (`adaptation_cache.py:106-118`). Then delete the tautological check at `:123-134`, rewrite `test_different_content_version_invalidates_cache` to bump the CV's real column through `PATCH /v1/cvs/{id}`, and add the endpoint-level regression: adapt → `PATCH` the CV → repeat the POST → expect a **new** `adaptation_id` and a second LLM call.
- **Note on spec vs design.** `cv-adaptation` R5 as written requires only `(cv_id, jd_text_hash)` and is therefore `MET`. The defect is against `design.md` D2 / §8.1. Either implement D2 or amend the design; leaving them divergent is how this shipped.

**F2 — JD prompt-injection sanitization does not exist. One of the two declared honesty layers is absent, with no implementation and no test.**

- **Evidence.** `design.md` §6.3 specifies `sanitize_jd_for_prompt()` with 4000-char truncation, code-fence neutralization, an injection regex and `<JD>…</JD>` delimiters, and names the adversarial test `test_jd_injection_neutralized`. A repo-wide search of `backend/app/**` for `sanitize_jd`, `sanitize_jd_for_prompt`, `<JD>` and `REDACTED` returns **zero** matches. The raw JD is interpolated straight into the user prompt at `backend/app/llm/groq_provider.py:208-211`, and the runner passes it through unmodified on the first attempt (`backend/app/services/adaptation_runner.py:257`). `tests/test_adaptation_validator.py` contains no injection case.
- **Why it matters.** `cvA-R4`'s scenario "Sanitización de prompt injection vía JD" is unimplemented, and `proposal.md` lists the risk with the mitigation "JD como dato no confiable; sanitización + test con payload malicioso" — the test does not exist either. The honest read is that the post-diff validator is currently the *only* line of defence for this attack surface. That validator does catch the canonical exploit (an injected skill such as `CISO` fails the subset check, since it is absent from the source) and it does check every token of length ≥ 3 in rewritten bullets, so the concrete "add CISO to the resume" payload is contained. What is not contained is an attacker who steers *how existing facts are framed* — the injected instruction can bias emphasis, ordering and framing inside the token-provenance rules. A spec scenario with no implementation is a CRITICAL on its own terms; the mitigation analysis says the blast radius is bounded, not that the requirement was met.
- **Fix.** Add `sanitize_jd_for_prompt()` per `design.md` §6.3 to `backend/app/services/adaptation_validator.py` (or a new `adaptation_prompt.py`), call it from `groq_provider.generate_adaptation` at `:208` before templating, cap the JD at 4000 chars, and land `test_jd_injection_neutralized` asserting both the transformed prompt and that an injected skill is rejected by `validate_adaptation`.

**F3 — `jd_text` is validated at ≥1 character, not ≥50, and a malformed JD reaches a paid LLM and consumes a slot.**

- **Evidence.** `backend/app/api/v1/adaptations.py:101-103`: `jd_text: str = Field(..., min_length=1, ...)`. `design.md` §3.3 and `cvA-R1`'s "Validación de payload" scenario require ≥50 (`JD_TOO_SHORT` → 422). The only 422 tests are `test_post_422_invalid_body_no_cv_id` and `test_post_422_invalid_body_empty_jd_text` — absent and empty, not short.
- **Why it matters.** A one-character JD creates a `pending` row, spawns the runner, calls the LLM with `max_tokens=4000`, and on completion charges one of the user's five monthly slots (`adaptation_runner.py:191`). The user spends quota and money on an adaptation built from no job description at all. Frontend validation masks this on `/profile` (`+page.svelte:422`), so the exposure is the public API — MCP-adapter consumers, direct clients, anything that skips the UI.
- **Fix.** `min_length=50` on the field (FastAPI then returns 422 with per-field detail, matching the spec), and add `test_post_422_invalid_body_short_jd_text` asserting a 40-character JD is rejected and no row is created.

### WARNING

**W1 — The deployed response contract does not match the four spec files.** `adaptations.py:136-140` (`poll_url` missing), `:273-276` (402 body is a bare string, no `current_tier`/`limit`/`upgrade_url`), `:283` (`NO_CV_FOUND`, not `CV_NOT_FOUND`), `:106-115` and `:118-134` (`id`/`cv_id`, not `adaptation_id`/`parent_cv_id`; flat `error_code`/`error_message`, not `error{code,message}`; no `score_estimated`), `:404` (route is `/adaptations/by-cv/{cv_id}`, not `/cvs/{id}/adaptations`). Each individual divergence is defensible; together they mean `openspec/specs/**` on disk does not describe the API and cannot be used as a contract or as an SDK source. Fix: either bring the endpoints to the specs or amend the specs — but do one of them, in writing, before archive.

**W2 — `outreach` and `brief` are absent from the payload rather than `null`.** `AdaptationDetail` (`adaptations.py:118-134`) declares neither field, so the JSON has no such keys. `cvA-R2`'s requirement statement ("La respuesta expone `outreach` y `brief` como `null` en Slice A") and the Slice-B/C contract commitment are unmet; a client written against the spec that reads `response.outreach` gets `undefined` rather than `null`, and a strict `null` check fails. Nothing populates them — there is no writer anywhere in the codebase, so the reserved-slots intent is safe, only the contract is wrong. Fix: `outreach: None = None` and `brief: None = None` on `AdaptationDetail`.

**W3 — `AdaptationResult.svelte` reuses none of the sub-components the requirement names, and owns none of the three states.** `frontend/src/lib/components/AdaptationResult.svelte:1-3` imports only `svelte-i18n` and a type. No `ScoreCard`, no `StrengthsGapsList`, no `ReasoningBox`; no pending branch; no failed branch; no retry button. `exp-R1` asks for all of these *of this component*. Today the state handling lives in the page (`+page.svelte:428-445`), which is the 700+-line page growth the proposal was trying to avoid. Fix: move the pending/failed/retry rendering into the component as designed and import the three sub-components; there is no score to pass yet (see W4), so `ScoreCard` can only be wired once `score_estimated` exists.

**W4 — `score_estimated`, `strengths`, `gaps`, `reasoning`, `gaps_against_jd` and `summary` exist nowhere: not in the prompt, not in the schema, not in the API.** `design.md` §3.3 and §6.1 specify all of them; `backend/app/llm/schemas.py:60-84` (`AdaptedCV`) has only `full_name`, `experience`, `skills`, `education`, `languages`; `groq_provider.py:97-102` never asks for them. This is why W3 cannot be fixed, and it is why the system prompt lacks the spec-mandated `gaps[]` instruction (`cvA-R4`). Fix: add the fields to `AdaptedCV`, require them in `CV_ADAPTATION_SYSTEM_PROMPT`, surface them on `AdaptationDetail`, and extend `validate_adaptation` to ignore them (they are model prose about the JD, not CV facts).

**W5 — `full_name`, `education` and `languages` are never validated.** `validate_adaptation` (`backend/app/services/adaptation_validator.py:796-896`) inspects skills, companies, titles, dates and bullet tokens — nothing else. The module docstring admits it at `:36-44`. Empirically confirmed: an adapted CV with `full_name: "Someone Else Entirely"`, `education: [{"degree": "PhD Nuclear Physics"}]` and `languages: ["Klingon"]` returns `ok=True` with **zero** violations against a source CV that contains none of them. `design.md` §7.2 check 6 ("Full name verbatim") was specified and not implemented, and the frontend renders `adapted.full_name` as the component's `<h3>` (`AdaptationResult.svelte:10`) — a fabricated name is the most visible thing on the page. Fix: add a normalized-equality check on `full_name` (the D1 normalizer makes this diacritic- and whitespace-tolerant) and a substring check on each `education[].degree` and `languages[]` entry, using the same `_is_substring_of` helper as the other fields.

**W6 — The skill/company guard admits invented short tokens; the documented `Go` → `Golang` coupling is real.** `_is_substring_of` (`adaptation_validator.py:161-174`) matches **bidirectionally**: `needle in hay or hay in needle`. With a realistic 12-skill source set, 23 of the 26 single lowercase letters are accepted as skill names, and 47 of 676 two-character tokens are accepted — every accepted token is a letter occurring in *some* source skill, so `R` passes against `Docker`, `React`, `PostgreSQL` or `TypeScript`. Multi-character inventions are still caught (`rust`, `kubernetes`, `terraform` → 3 violations). The `Go` → `Golang` coupling is confirmed: `_is_substring_of("golang", {"go"})` is `True` via the `hay in needle` branch, which is the same branch that admits `R`. So the one-line guard that would close this (require equality, or require both sides ≥ some length) genuinely would break a legitimate rewrite. `docs/audit/STATUS.md`'s "11 de 16" is one instance of a wider hole; I could not reproduce that exact figure because the probe list is not recorded. Fix: keep the bidirectional branch but require `len(needle) >= 3` on the `hay in needle` direction (so `go` → `golang` survives, `r` → `docker` does not) and log the rejected alias so the rule can be tuned from evidence.

**W7 — The sweeper deletes rows instead of failing them; `error_code = "TIMEOUT"` can never be produced.** `design.md` §5.4 specifies `fail_stale_pending(max_age_minutes=10)` → `status='failed', error_code='TIMEOUT'`, and states explicitly: "El sweep no borra las filas — sólo marca `failed`." The shipped endpoint runs two `DELETE`s — completed rows older than **90 days** and pending rows older than **1 hour** (`backend/app/api/v1/internal/adaptations.py:52-53`, `:105-121`). Consequences: the `TIMEOUT` code in the spec's error table (`design.md` §3.4) is dead; a client polling an orphaned job gets a 404 instead of a terminal `failed`, so `frontend/src/lib/stores/adaptation.ts` treats it as a generic failure; and 90-day deletion of completed adaptations is **data deletion nobody asked for** — it is in no proposal, no design, no spec, and no task. Also note the auth differs from the design (`X-Backend-API-Key` header against `settings.backend_api_key`, `:55-73`, versus a body HMAC against a dedicated `adaptation_cleanup_token`). Fix: restore the mark-failed path for pending rows (or document the delete as an accepted deviation), and get an explicit decision on the 90-day completed-row deletion before it ships.

**W8 — `ADAPTATION_ENABLED` defaults to `False`, contradicting `tasks.md` PR1.6 and `design.md` §10.4.** `backend/app/core/config.py:91`: `adaptation_enabled: bool = Field(default=False, validation_alias="ADAPTATION_ENABLED")`. Both artifacts say `ADAPTATION_ENABLED: bool = True`. `backend/app/api/deps.py:248-264` and the router-level dependency are correct and complete (see the positive result below), but the shipped default leaves the whole feature **off** unless the environment sets the variable — and `docs/audit/STATUS.md`'s deploy runbook (step 3, manual Render deploy) never mentions it. Fix: either change the default to `True` as designed, or correct both artifacts and add `ADAPTATION_ENABLED=true` to the documented deploy steps. Right now the two sources of truth disagree about whether the feature is live.

**W9 — Polling aborts on the first network error and exposes no manual status check.** `frontend/src/lib/stores/adaptation.ts:112-123`: any exception from `apiClient.getAdaptation` immediately sets `status: 'failed'` and returns. `exp-R4` requires continuing with the next scheduled poll and failing only after 3 *consecutive* errors. A single transient 5xx therefore destroys a job that is still running server-side, and the user is shown a failure for work that may have completed and been charged. Separately, the give-up branch sets `POLL_TIMEOUT` (`:140-145`) but the page offers no "Verificar estado" action, which `exp-R4` requires. Fix: count consecutive errors and abort on the third; expose `pollAdaptation` (already exported at `:173`) from the page as the manual status check.

**W10 — `get_cached` has no `owner_user_id` predicate.** `design.md` §8.1 requires the cache hit to require `owner_user_id == current_user.id` ("multi-tenant; mismo JD por dos usuarios NO hit"). The query filters on `parent_cv_id`, `jd_text_hash`, `status` and `created_at` only (`backend/app/services/adaptation_cache.py:106-118`). Multi-tenancy today rests entirely on the RLS owner policy, which is `FORCE`d (`016_rls_cv_adaptations.py:47-48`) and therefore sound; but the design's defence-in-depth layer is missing, and the function would become cross-tenant the moment it were called with a service-bound session. `tests/test_adaptation_cache.py:314-336` explicitly declines to test this, deferring to RLS. Fix: add `owner_user_id` to the signature and the predicate — a one-line change that makes the code match the design.

**W11 — `/profile/+page.svelte` is 870 lines, past the design's own 700-line CI guard.** `design.md` §12 R8 states the mitigation is "Validación en CI: `wc -l frontend/src/routes/profile/+page.svelte < 700`". The file is 870 lines (`frontend/src/routes/profile/+page.svelte`), of which PR3 contributed ~310 (`git show --stat 12dc7da`). No such CI check exists. `proposal.md` §Risks named page growth as a Medium risk with the mitigation "Componente compartido". Fix: extract the adaptation section into its own component and add the `wc -l` guard to CI so the budget is enforced rather than asserted.

### SUGGESTION

**S1 — `CVAdaptation` declares `Integer` for columns that migration 015 creates as `BigInteger`.** `backend/app/db/models.py:711-715` and `:722-725` vs `backend/alembic/versions/015_cv_adaptations.py:56-68`. A subscription that renews on the 20th does not reset `adaptations_used`; the user keeps the previous month's count until the 1st. This is inherited Sprint-2 semantics and `bill-R4` asks only that the mechanism match `matches`, so I am not raising it as a finding — but the spec's wording ("cuando la suscripción se renueva (`current_period_start` nuevo)") does not describe what the code does, and the same mismatch will apply to matches.

**S4 — The dead `content_version` check in `get_cached` reads like a guard.** `backend/app/services/adaptation_cache.py:123-134`, with a five-line comment explaining a defensive check that can never fail in production. It is the single most misleading artifact in this change: it *documents* invalidation while performing none, and it is what the green test at `test_adaptation_cache.py:251` is really asserting. Once F1 is fixed this code should be deleted rather than kept.

**S5 — `adaptation-sweeper.yml` hardcodes a production fallback URL.** `.github/workflows/adaptation-sweeper.yml:19`: `${{ vars.RENDER_BACKEND_URL || 'https://asistcv-backend.onrender.com' }}`. ## 6. Scope creep check

The shipped code contains five things the proposal did not ask for. Naming them is not an accusation — three are defensible or were forced by later audit work — but none is recorded in `proposal.md`, `design.md` or `tasks.md`, so the artifact set understates the surface area of the change.

1. **Retention deletion of completed adaptations at 90 days.** `backend/app/api/v1/internal/adaptations.py:52` and `:105-113`. `design.md` §5.4 says the opposite — "El sweep no borra las filas — sólo marca `failed`" — and deletion appears in no proposal, design or spec. This is unreviewed **data deletion** on a table the same spec calls an audit trail (`cv-management` R2: "conservadas para auditoría"). Needs an explicit decision. See **W7**.
2. **Migration 019, renaming `jd_text_encrypted` → `jd_text`.** `backend/alembic/versions/019_rename_adaptations_jd_text.py`. A post-Slice-A correction of a column name that claimed encryption that was never implemented. Legitimate and well-documented in the migration, but it is a fifth migration in a change that specified four, and it is invisible to `tasks.md`.
3. **Migration 021, rescoping the partial unique index.** `backend/alembic/versions/021_cv_adaptations_pending_uq.py`. A genuine defect fix (see item 4 in §4), but a fifth migration in the same change and a schema change the design never contemplated. Also invisible to `tasks.md`.
